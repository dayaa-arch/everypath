# 0004: 承認の記録は `.everypath/review/` に 1 件 1 ファイルで足していく

日付: 2026-10-22
状態: 採用（0003 の記録の置き場を置き換える。「承認の記録は常に git 管理する」という 0003 の意図は変えない）
影響する不変条件: R-01（書く先は `.everypath/review/` と `.everypath/.gitignore` で、`.everypath/` の中に収まる。文言は変えない）、R-04（読めない記録も衝突の印も警告にする）

## 背景

`SPEC.md` §16 フェーズ 3 のチーム向け機能は、承認者と承認日時をビューアに出すことと、git で共有した承認の記録が合流で壊れないことを求める。今の `.everypath/review.json` は整形した 1 つの JSON で、2 本のブランチが別々の状態を承認しただけで同じ塊を書き換え、git が衝突の印を残す。印の残ったファイルは JSON として読めず、承認がすべて消えたように見え、書き込みも止まる。同じ状態を 2 人が違う内容で承認したときは、どちらか一方が黙って勝つ。

## 決定

- 承認と取り消しは、1 件ずつ `.everypath/review/<id>.jsonl` に 1 行で書く。`<id>` はその行の sha256 の先頭 16 桁。everypath は記録を作るだけで、書き換えも削除もしない。2 本のブランチは違う名前のファイルを足すだけなので、`git merge` も `.gitattributes` を読まない `git merge-tree` も衝突しない。
- 記録は、書いた人が見ていたその状態の生きた記録を `supersedes` に並べて置き換える。誰にも置き換えられていない記録が生きている。生きた記録が同じ hash の承認だけなら、いちばん新しい承認を `graph.json` の `review.approval` に出す。違う hash の承認、承認と取り消し、承認と読めない記録が並べば `review.conflict` にし、承認済みにしない。`scan` と `check` は状態ごとに警告を 1 件出し、ビューアは記録ごとに承認者、時刻、版を出す。承認し直すか取り消すと食い違いは終わる。
- 承認の無いリポジトリの `graph.json` は前と同じバイト列になる（`review` は生きた承認があるときだけ書く）。
- `.everypath/review.json` は読み続け、二度と書かない。各項目は、何も置き換えない承認の記録として同じ集合に入るので、今日の取り消しが旧項目を id で名指しできる。git の衝突の印が残ったファイルは両側を読み、警告を 1 件出す。
- 旧と新の混在（接ぎ木 1）。生きた旧形式の承認と `review/` の記録が同じ状態に並ぶと警告する。新しい記録が旧承認に勝つのは `supersedes` で名指ししたときだけ。
- 読めない記録は閉じる（接ぎ木 2）。状態が読めて中身が読めない記録（新しい版、形の違う欄）は名指しした記録を置き換え、その状態を食い違いにする。状態すら読めない記録（JSON でない、名前が違う、リンク、32 KiB 超）は、承認のあるすべての状態を食い違いにする。どちらも古い承認を生き返らせない。
- 読んだ記録の再利用（接ぎ木 3）。記録の名前は中身の hash で書き換えられないので、serve のプロセスは一度読めた記録を名前で覚え、次の再スキャンでは新しい記録だけを読む。5,000 件で、最初のスキャン 193 ms に対し以後のスキャンは 40 ms（記録の無い同じリポジトリは 46 ms と 32 ms。`scripts/bench-review.ts`）。
- git の管理。`init` が書いた 2 行（`.everypath/*`、`!.everypath/review.json`）は `review/` を無視する。記録を書く前に `.everypath/.gitignore` へ `!review/` と `review/*.tmp` を足し、入れ子の `.gitignore` で管理に戻す。既存のリポジトリは `init` をやり直さなくてよい。新しいリポジトリには `init` も同じファイルを書く。
- `by` は今までどおり `git config user.name`、`USER`、空の順で、サーバーが埋める。表示名であって署名ではない。メールアドレスは記録しない。

## 捨てた案

- `review.json` を 1 行 1 項目にして `.gitattributes` の `merge=union` で合流させる（arena の候補 1）。GitHub などのサーバー側の合流は `.gitattributes` を読まず、同じ隙間に入る初回承認どうしが衝突する。整形ツールで複数行になると読めなくなる。
- 1 状態 1 ファイル（`review/<状態名>.json`）。同じ状態の食い違いが git の衝突として残り、日本語の状態名をファイル名にすると macOS（NFD）と Linux でバイトが変わる。
- git のマージドライバ。`.git/config` に登録が要り、リポジトリに commit できず、R-01 で everypath は書けない。
- `review.json` のまま、読む側が衝突の印に耐える。別々の状態の承認も衝突し、人がファイルを手で直す。旧ファイルの読み込みにだけこの考えを残した。

## 影響

`docs/REQUIREMENTS.md` の決定記録に追加し、0003 の行に置き換えを書く。`SPEC.md` §4、§6.1、§6.2、§8、§11、§12.2、§15、§16、§17.6 を新しい形に直す。`docs/specs/server.md` の条件 4 と 9、`docs/specs/init.md` の条件 2 と 3 に注記する。機能仕様は `docs/specs/team-review.md`。残る端: 記録のファイルを消すと、それが置き換えていた記録が生き返る（git には削除として見える。手で `review.json` を書き換えるのと同じ）。

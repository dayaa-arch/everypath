# フェーズ 3 計画

`SPEC.md` §16 フェーズ 3 の 3 項目を、触るファイルで 2 つの波に分ける。各項目は機能仕様（`docs/specs/<slug>.md`）を持つ 1 つの PR になる。フェーズ 1 から持ち越した穴のうち「前回承認日時」はチーム向け機能（P3-3）に含めて埋める。残る 3 つ（TypeOK のグラフ表示、Linux 監視の実機確認、TLC のメモリ上限）はどの項目の前提でもないので、後回しにする（2026-10-22 の判断）。

## 進め方

フェーズ 2 と同じく、各 PR は my-mode の Spec-driven feature で進める。積み上げる PR は、統合用のブランチを経由せず、直前の PR のブランチから直接切る（フェーズ 2 で、統合ブランチ経由の積み上げを GitHub が衝突と判定したため）。

## 第 1 波（並行、ファイルが重ならない）

- [ ] P3-1 Go、Rust、Java、Kotlin の import 解決。触るのは `src/core/imports.ts` と、その文脈を作る最小限の箇所。
- [ ] P3-2 関数単位の証明。`.everypath/proofs.json`（`SPEC.md` §10.5）を読んで `status.proof` に反映し、Dafny と Verus の出力を取り込むアダプタ、`everypath prove`、「仕様と証明を書く」指示（§13）を足す。Dafny と Verus はこの機械に無いので、道具の実物での確認は作者の許可を得てから行う。

## 第 2 波（P3-2 の後、P3-2 のブランチから切る）

- [ ] P3-3 チーム向け機能。承認者と前回承認日時をグラフとビューアに出す（持ち越しの穴）。複数人が `review.json` を git で共有したときのマージを扱う。設計は第 1 波と並行して architect で決める。

## 終わり方

- [ ] 全 PR をマージした `main` で、フェーズ 1 の受け入れ基準 12 項目と各仕様の完了条件を確かめる。

## 付録. 危険

- 証明の道具が手元に無いので、P3-2 の出力の読み取りは、道具の公式の出力例か、許可を得て導入した実物で確かめる。作り話の出力でテストを書かない。
- P3-2 と P3-3 はどちらも `src/core/scan.ts` とビューアに触る。P3-3 を P3-2 のブランチから切ることで衝突を避ける。
